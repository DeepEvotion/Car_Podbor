# Исполнительное техническое задание для AI-агента

## Проект

Игровой помощник по выбору автомобиля с персональным подбором, адаптивным тестом, дуэлями автомобилей, гаражом и системой друзей.

## Статус документа

Версия 1.0. Документ предназначен для AI-агента, который должен самостоятельно создать рабочий сайт в пустом репозитории, запустить его локально, покрыть критическую бизнес-логику тестами и предоставить понятный результат для проверки.

## 1. Главная задача агента

Создать мобильный веб-сайт, который принимает свободное описание пожеланий пользователя, помогает уточнить практические потребности и вкусы, проводит короткий игровой тест, при необходимости показывает дуэли автомобилей, а затем выдаёт несколько реальных автомобилей из локального каталога.

Сайт должен объяснять каждую рекомендацию через проверяемые факты, показывать компромиссы, позволять менять ответы, пересчитывать результат, сохранять автомобили в гараж и делиться гаражом с друзьями.

Основной источник фактов о технических характеристиках — локальный каталог проекта. Языковая модель может помогать понять пользовательский текст и сформулировать объяснение, но не может самостоятельно придумывать технические характеристики, отменять обязательные ограничения или добавлять автомобили в каталог.

## 2. Обязательный результат работы агента

Агент должен предоставить:

1. Запускаемый сайт с главным пользовательским сценарием.
2. Локальный каталог автомобилей минимум из 20 разнообразных записей.
3. Рабочий алгоритм фильтрации и ранжирования.
4. Игровой адаптивный тест.
5. Минимум 3–5 дуэлей автомобилей в рамках одного подбора.
6. Экран результата с рекомендациями и объяснениями.
7. Редактирование ответов и повторный расчёт.
8. Личный гараж с сохранением автомобилей.
9. Профиль и просмотр гаража по ссылке.
10. Базовую механику друзей или её локальный демонстрационный режим, если серверная авторизация ещё не реализована.
11. Тесты алгоритма, граничных случаев и ключевых пользовательских сценариев.
12. README с командами запуска, переменными окружения, описанием архитектуры и ограничениями текущей версии.

## 3. Принцип выполнения

Агент должен сначала обследовать репозиторий и существующие файлы. Если репозиторий пустой, создать проект с нуля. Нельзя начинать с декоративных экранов, оставляя движок подбора на уровне заглушки.

Порядок реализации должен быть таким:

1. архитектура и типы данных;
2. каталог и тестовые профили;
3. алгоритм подбора;
4. API или серверные функции;
5. состояние пользовательского сценария;
6. интерфейс основных экранов;
7. гараж и ссылки;
8. AI-адаптер;
9. визуальная полировка;
10. тестирование и проверка сборки.

Каждый этап должен оставлять приложение запускаемым. Нельзя скрывать ошибки пустым интерфейсом или подставлять случайные автомобили для заполнения списка.

## 4. Зафиксированное техническое решение

Проект реализуется как адаптивное веб-приложение с отдельным frontend и backend API. Клиент отвечает за интерфейс и состояние пользовательского сценария. Backend отвечает за авторизацию, каталог, алгоритм подбора, AI-адаптер, гараж, друзей и доступ к данным.

### Frontend

- React;
- Vite;
- TypeScript в строгом режиме;
- React Router;
- TanStack Query для запросов и кэширования;
- Zustand или React Context для состояния прохождения теста;
- Tailwind CSS;
- Zod для проверки клиентских форм;
- Vitest и React Testing Library;
- Playwright для end-to-end сценариев.

### Backend

- Python 3.12+;
- FastAPI;
- Pydantic v2;
- SQLAlchemy 2.0;
- Alembic;
- PostgreSQL 16+;
- `psycopg` или async-драйвер `asyncpg`;
- Pytest;
- Ruff и mypy.

### Инфраструктура

- Docker Compose для frontend, backend и PostgreSQL;
- Nginx или аналогичный reverse proxy для production;
- `.env.example` с описанием обязательных переменных;
- seed-скрипт для каталога и демо-аккаунтов.

### Почему выбран FastAPI

FastAPI лучше соответствует API-first архитектуре этого проекта. Он использует типизацию Python, автоматически формирует OpenAPI-документацию, удобно работает с Pydantic-схемами и подходит для AI-интеграций.

Flask тоже может решить задачу, но потребует самостоятельного выбора и настройки большего количества компонентов для схем, документации, валидации и структуры API. Flask использовать только при наличии сильной причины, связанной с уже существующим кодом команды.

Django REST Framework является допустимой альтернативой, если приоритетом становится встроенная админ-панель, сложная авторизация и большое количество CRUD-сущностей. Для текущего продукта FastAPI сохраняет backend легче и прозрачнее.

### Правило хранения данных

PostgreSQL является основной базой данных проекта. Все сущности пользователей, профилей, результатов подбора, дуэлей, гаражей, ссылок и друзей хранятся в PostgreSQL. SQLite в проекте не используется.

Схема изменяется через Alembic migrations. Нельзя создавать таблицы автоматически при старте production-сервера. Нельзя использовать PostgreSQL-логику, скрытую внутри UI.

### Правило авторизации

Backend реализует регистрацию, вход, выход и проверку сессии. Предпочтительный способ — HttpOnly Secure cookie с серверной сессией или короткоживущим access token и refresh token. Токены авторизации нельзя хранить в `localStorage`.

Гостевой подбор работает без регистрации и хранится в браузере до переноса результата в аккаунт.

### Правило работы AI

AI-провайдер подключается только через backend-адаптер. Frontend не получает секретный ключ и не обращается к AI-провайдеру напрямую. При отсутствии `AI_API_KEY` включается `DeterministicAIProvider` с готовым разбором, библиотекой вопросов и шаблонными объяснениями.

### Почему выбран раздельный frontend и backend

- frontend можно развивать независимо от алгоритма;
- backend защищает каталог, авторизацию и приватные данные;
- алгоритм тестируется без браузера;
- PostgreSQL подключается напрямую к API;
- AI-ключи остаются на сервере;
- frontend можно разместить отдельно от API;
- мобильная адаптивность контролируется на уровне клиентского приложения.

### 4.1. Архитектура развёртывания

#### Локальная разработка

```text
Docker Compose
├── frontend — React/Vite dev server
├── backend — FastAPI
└── postgres — PostgreSQL
```

Команда запуска должна поднимать все необходимые сервисы одной командой. Переменные подключения задаются через `.env` на основе `.env.example`.

#### Демонстрационный стенд

Для показа жюри достаточно одного сервера или одной виртуальной машины:

```text
Nginx
├── /       → собранный React frontend
└── /api/   → FastAPI

PostgreSQL → отдельный контейнер или managed database
```

Frontend должен обращаться к API через относительный путь `/api`. Это позволяет размещать frontend и backend на одном домене и уменьшает сложность CORS и cookies.

#### Production-направление

Архитектура должна допускать следующие шаги без переписывания продукта:

1. вынести PostgreSQL в managed database с резервным копированием;
2. запускать несколько stateless-контейнеров FastAPI за reverse proxy;
3. добавить connection pooling для PostgreSQL;
4. подключить Redis для кэша каталога, rate limiting и временных данных дуэлей;
5. вынести изображения автомобилей в объектное хранилище или CDN;
6. добавить фоновые задачи для тяжёлых AI-запросов и аналитики;
7. подключить мониторинг ошибок и метрик.

Эти компоненты не обязательны для MVP. Их отсутствие не должно блокировать локальный запуск и демонстрацию.

### 4.2. API-контракт

Backend является единственным владельцем бизнес-логики. Frontend не рассчитывает рейтинг самостоятельно и не содержит копий правил фильтрации.

FastAPI публикует OpenAPI-схему. На её основе можно генерировать TypeScript-типы для frontend. Ручное дублирование DTO между Python и TypeScript свести к минимуму.

Базовые группы API:

- `/api/auth` — регистрация, вход, выход, текущая сессия и демо-вход;
- `/api/catalog` — публичные данные каталога;
- `/api/recommendations` — запуск и получение результатов подбора;
- `/api/duels` — создание сессии, получение пары и сохранение выбора;
- `/api/garage` — сохранение и изменение автомобилей;
- `/api/profiles` — профиль и настройки видимости;
- `/api/shares` — создание и отзыв ссылок;
- `/api/friends` — запросы и подтверждённые связи;
- `/api/ai` — разбор свободного текста и выбор вопросов.

Каждый endpoint должен иметь Pydantic request/response schema, код ошибки и тест. Ошибки API возвращать в едином формате:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте заполненные поля",
    "fields": {}
  }
}
```

## 6. Границы MVP

### Входит в реализацию

- свободное описание пожеланий;
- короткий рациональный опрос;
- визуальные карточки и дуэли;
- каталог реальных моделей и модификаций;
- обязательные и желательные условия;
- детерминированный подбор;
- объяснения и компромиссы;
- неизвестные значения и пропуски;
- повторный расчёт;
- сохранение в гараж;
- настройки видимости;
- ссылка на профиль или гараж;
- минимальная система друзей по коду или ссылке.

### Можно реализовать заглушкой

- внешний AI-провайдер;
- отправка email;
- push-уведомления;
- полноценный чат;
- комментарии;
- реальное публичное размещение в интернете.

### Не реализовывать

- покупку автомобиля;
- кредитование;
- расчёт полной стоимости владения;
- сбор паспорта, адреса, телефона и водительского удостоверения;
- автоматический массовый сбор данных с сайтов;
- выдачу неподтверждённых характеристик как фактов.

## 7. Пользовательские роли

### Гость

Может пройти подбор, получить результат, сохранить его локально и открыть демонстрационный гараж. Регистрация не должна быть обязательной для основного сценария.

### Пользователь

Может сохранять гараж на сервере, создавать ссылку, управлять видимостью и добавлять друзей.

### Друг

Может видеть только те данные, которые разрешил владелец. Друг не получает доступ к бюджету, исходному профилю и личным заметкам без отдельного разрешения.

## 8. Пользовательские маршруты

### 8.1. Главная страница

Должны быть видны:

- краткое описание пользы сервиса;
- примерная длительность теста от 2 до 4 минут;
- кнопка начала;
- переход к гаражу;
- переход к просмотру профиля по ссылке.

Главная страница должна объяснять, что пользователь может пропускать вопросы и менять ответы.

### 8.2. Свободное описание

Поля:

- многострочное описание;
- быстрые подсказки с примерами;
- кнопка «Не знаю, чего хочу»;
- кнопка продолжения.

Если AI-провайдер отключён, текст сохраняется, а профиль создаётся из выбранных быстрых сценариев или нейтрального профиля.

### 8.3. Рациональные вопросы

Минимальный набор:

1. сценарий использования;
2. количество пассажиров;
3. количество вещей;
4. город, трасса, плохие дороги или смешанный режим;
5. коробка передач;
6. тип силовой установки;
7. бюджет или неизвестный бюджет;
8. обязательные условия;
9. желательные условия.

Каждый вопрос имеет варианты «не знаю», «пропустить» или «без разницы», если это применимо.

### 8.4. Эмоциональные вопросы

Минимальные шкалы:

- сдержанный и яркий;
- ретро и современный;
- современный и футуристичный;
- уютный и технологичный;
- спокойный и спортивный;
- практичный и статусный;
- компактный и основательный.

Шкалы хранятся числом от 0 до 1. Пропуск хранится как `null`, а не как 0.5.

### 8.5. Дуэли

В одной дуэли показываются две карточки, но пользователь не должен видеть полный набор характеристик автомобилей. Цель дуэли — сравнить конкретное различие, которое помогает определить вкус или приоритет, а не выбрать машину по технической таблице.

Перед показом пары система должна определить 1–3 наиболее различающих признака. Выбор признаков выполняется на основе:

- разницы между двумя автомобилями;
- неопределённости в профиле пользователя;
- влияния признака на текущий рейтинг;
- понятности признака для человека без автомобильных знаний;
- отсутствия дублирования уже показанных сравнений.

Примеры фокуса дуэли:

- «уютный салон или спортивная посадка»;
- «компактный городской формат или больше места для поездок»;
- «сдержанный дизайн или яркая внешность»;
- «простота и практичность или технологичность»;
- «низкая посадка или высокий клиренс»;
- «спокойный характер или динамичный характер».

Карточка дуэли должна содержать:

- изображение или визуальный образ автомобиля;
- название модели только в том объёме, который предусмотрен режимом игры;
- короткое описание выбранного различия;
- 1–3 сравнительных признака;
- ответы «выбрать левую», «выбрать правую», «нравятся обе», «не нравится ни одна», «пропустить».

Полные поля каталога, точный бюджет, все технические параметры и длинная таблица характеристик в дуэли не выводятся. Подробные характеристики доступны после дуэли в карточке результата.

Пример структуры фокуса:

```ts
type DuelFocus = {
  key: string
  title: string
  leftLabel: string
  rightLabel: string
  leftValue: string
  rightValue: string
  relatedDimensions: string[]
  reason: 'style' | 'practicality' | 'comfort' | 'road' | 'technology'
}
```

Доступны ответы:

- выбрать левую;
- выбрать правую;
- нравятся обе;
- не нравится ни одна;
- пропустить.

На мобильном экране карточки должны располагаться вертикально или переключаться жестом. Важные характеристики не должны быть спрятаны только за анимацией.

### 8.6. Результат

Показывать от 3 до 5 разных автомобилей, если столько найдено. Для каждого автомобиля вывести:

- марку, модель, поколение и модификацию;
- общий балл только как техническое поле, не как единственное объяснение;
- 2–4 причины совпадения;
- сильные стороны;
- компромиссы;
- неизвестные данные;
- ближайшую альтернативу;
- действие «Сохранить в гараж»;
- действие «Изменить ответы».

Результат должен включать три акцента:

- «Разумный выбор»;
- «Выбор сердцем»;
- «Твой баланс».

Если подходящих машин меньше трёх, показывать фактическое число. Если подходящих машин нет, показывать причину и конкретное ограничение, которое исключило кандидатов.

### 8.7. Карточка автомобиля

Показывать только данные, присутствующие в каталоге:

- основные характеристики;
- тип кузова;
- места;
- багажник или класс вместимости;
- привод;
- коробка;
- силовая установка;
- клиренс или класс проходимости;
- ценовой диапазон, если он есть;
- качество данных и источник проверки.

Субъективные теги стиля выводить как редакционную оценку, а не как технический факт.

### 8.8. Гараж

Пользователь может сохранять автомобиль со статусом:

- интересно;
- рассматриваю;
- мечта;
- владею.

Можно добавить личную заметку, изменить статус, удалить запись, открыть сравнение и создать ссылку.

### 8.9. Профиль и друзья

Профиль содержит отображаемое имя, аватар по желанию, гараж и настройки видимости. Добавление друга выполняется через код или ссылку с подтверждением обеих сторон.

В первой версии друзья могут просматривать разрешённые машины, ставить реакции и участвовать в игре «угадай машину друга».

### 8.10. Регистрация и демо-аккаунты

На странице регистрации необходимо разместить отдельный блок «Посмотреть демо» рядом с обычной регистрацией и входом. Жюри должно открыть готовый профиль одним нажатием без ввода личных данных и без самостоятельного прохождения теста.

Создать минимум три демо-аккаунта:

1. **Демо-первый автомобиль** — профиль начинающего пользователя, сохранённые городские автомобили и один незавершённый результат.
2. **Демо-семья и путешествия** — профиль с пятью пассажирами, большим багажом, поездками и несколькими сохранёнными кроссоверами или универсалами.
3. **Демо-выбор сердцем** — профиль с выраженными эмоциональными предпочтениями, историей дуэлей, сохранёнными яркими или спортивными автомобилями и сравнением двух моделей.

Для каждого демо-аккаунта заранее создать:

- профиль;
- гараж минимум из 3 автомобилей;
- один или несколько результатов подбора;
- историю дуэлей;
- публичную или доступную по демо-ссылке карточку гаража;
- понятное отображаемое имя без персональных данных.

В блоке демо показывать карточки с названием профиля, кратким описанием и кнопкой «Открыть демо». После нажатия создать сессию выбранного демо-пользователя и открыть его профиль или гараж.

Демо-аккаунты должны иметь флаг `isDemo`. Для них запрещены:

- просмотр реальных персональных данных;
- изменение других демо-профилей;
- доступ к секретам сервера;
- изменение seed-данных, которое сохраняется между сбросами демо.

Изменения в демо-профиле можно разрешить только в рамках временной сессии. Для повторной демонстрации предусмотреть кнопку «Сбросить демо» или серверную команду `npm run db:seed`.

На странице регистрации также показать обычный путь создания аккаунта. Демо-вход не должен маскироваться под полноценную регистрацию.

## 11. Алгоритм подбора автомобилей

### 11.1. Общая схема

Алгоритм состоит из следующих этапов:

1. валидация профиля;
2. нормализация значений;
3. проверка обязательных условий;
4. формирование допустимых кандидатов;
5. расчёт рационального совпадения;
6. расчёт эмоционального совпадения;
7. расчёт полноты данных;
8. расчёт итоговых режимов;
9. удаление дублей и диверсификация;
10. генерация объяснений;
11. стабильная сортировка;
12. сохранение версии результата.

### 11.2. Нормализация

Перед расчётом привести профиль к единому формату:

- убрать дубли требований;
- привести строки к enum-значениям;
- ограничить числа допустимым диапазоном;
- преобразовать бюджет в диапазон;
- преобразовать пассажиров в минимально необходимое количество;
- преобразовать эмоциональные ответы в шкалы `0..1`;
- сохранить пропуски как `null`;
- сохранить неизвестность отдельно от отрицательного ответа.

### 11.3. Обязательные условия

Обязательное условие имеет тип:

```ts
type Requirement = {
  key: RequirementKey
  value: string | number | boolean
  source: 'user' | 'inferred'
}
```

Минимальные обязательные условия:

- минимальное количество мест;
- коробка передач;
- тип силовой установки;
- бюджет;
- минимальная вместимость;
- пригодность для плохих дорог;
- тип кузова, если выбран явно.

Проверка возвращает одно из значений:

```ts
type ConstraintState =
  | 'satisfied'
  | 'violated'
  | 'unknown'
  | 'not_applicable'
```

Правила:

- `violated` исключает автомобиль;
- `satisfied` допускает автомобиль;
- `not_applicable` не влияет на результат;
- `unknown` не может считаться выполненным обязательным условием.

Для неизвестного обязательного условия в MVP использовать консервативное правило и исключать автомобиль из блока подтверждённых рекомендаций. При отсутствии других вариантов можно показать его в отдельном блоке «нужно проверить», но явно указать неизвестное поле.

### 11.4. Проверка бюджета

Если бюджет задан диапазоном `[userMin, userMax]`, а автомобиль имеет диапазон `[carMin, carMax]`, использовать пересечение диапазонов.

```text
budgetMatch = intersectionLength(userRange, carRange) / userLength
```

Если пользователь указал только максимум, автомобиль проходит обязательное условие при `carMin <= userMax`.

Если бюджет неизвестен, не исключать автомобили по цене и выставлять `budgetMatch = null`.

Если автомобиль не имеет цены, обязательное бюджетное условие имеет состояние `unknown`.

### 11.5. Проверка пассажиров и багажа

Автомобиль проходит требование по пассажирам при подтверждённом `seats >= requiredPassengers`.

Для багажа использовать нормализованные классы:

```text
small < medium < large
```

Если есть точный объём багажника, преобразовать его в класс через конфигурационные пороги. Если точного объёма нет, использовать только явно заданный класс.

### 11.6. Рациональный балл

Рациональный балл находится в диапазоне `0..1`.

Предлагаемые веса:

```text
сценарии использования       0.25
пассажиры                    0.15
багаж                        0.10
дороги                       0.15
коробка передач              0.10
силовая установка            0.10
бюджет                       0.10
желательные условия          0.05
```

Веса применяются только к известным и применимым полям. Если поле пропущено, его вес исключается из знаменателя, а итог нормализуется на сумму использованных весов.

Пример:

```text
rational = sum(weight_i * match_i) / sum(weight_i for known fields)
```

Значения совпадения:

- точное совпадение — `1.0`;
- частичное совпадение — значение от `0.25` до `0.75`;
- отсутствие совпадения по желательному условию — `0.0`;
- неизвестное значение — поле исключается из расчёта и попадает в объяснение.

### 11.7. Эмоциональный балл

Эмоциональный балл рассчитывается как близость между вектором пользователя и вектором автомобиля.

Для каждого известного измерения:

```text
dimensionMatch = 1 - abs(userValue - carValue)
```

Итог:

```text
emotional = weightedAverage(dimensionMatch)
```

Вес измерения зависит от уверенности пользователя:

```text
effectiveWeight = baseWeight * confidence
```

При ответе «оба нравятся» уверенность повышается слабо. При последовательном выборе одного направления уверенность увеличивается. При ответе «ни один» изменение профиля не выполняется.

### 11.8. Полнота данных

Полнота данных показывает, насколько результат можно обосновать:

```text
completeness = knownRelevantFields / relevantFields
```

Не использовать полноту данных как замену пригодности автомобиля. Она только помогает выбрать между одинаково подходящими вариантами.

### 11.9. Итоговый балл

Базовая формула:

```text
final =
  0.55 * rational +
  0.35 * emotional +
  0.10 * completeness
```

Веса должны находиться в конфигурации алгоритма:

```ts
const ALGORITHM_CONFIG = {
  version: 'mvp-1.0',
  weights: {
    rational: 0.55,
    emotional: 0.35,
    completeness: 0.10,
  },
}
```

Алгоритм не должен добавлять случайность. При одинаковых входных данных порядок должен совпадать.

### 11.10. Три режима результата

#### Разумный выбор

```text
reasonable = 0.75 * rational + 0.15 * emotional + 0.10 * completeness
```

#### Выбор сердцем

```text
heart = 0.25 * rational + 0.65 * emotional + 0.10 * completeness
```

#### Твой баланс

```text
balance = 0.55 * rational + 0.35 * emotional + 0.10 * completeness
```

Жёсткие ограничения применяются до всех трёх режимов. Режим «Выбор сердцем» не может вывести автомобиль, нарушающий обязательное условие.

### 11.11. Штрафы

Штрафы применять только к желательным условиям и качеству данных. Нельзя использовать штрафы для обхода обязательного фильтра.

Предлагаемые значения:

```text
неизвестное важное поле       -0.03
нарушение желательного поля   -0.08
неполный стиль                -0.02
```

Штрафы должны быть ограничены так, чтобы автомобиль с лучшим совпадением не проигрывал случайно из-за одного неизвестного второстепенного поля.

### 11.12. Дубли и диверсификация

В итоговом списке не должно быть нескольких одинаковых автомобилей из разных модификаций, если модификации не меняют существенную часть требований пользователя.

Использовать ключ группировки:

```text
brand + model + generation
```

В итоговый список сначала включать лучший вариант группы. Вторую модификацию добавлять только при существенном отличии по коробке, силовой установке, цене или обязательному параметру.

При наличии большого числа похожих моделей применять штраф за сходство с уже выбранными кандидатами. Для MVP достаточно ограничить одну группу одной моделью.

### 11.13. Стабильная сортировка

Сортировать по:

1. итоговому баллу по убыванию;
2. рациональному баллу по убыванию;
3. полноте данных по убыванию;
4. идентификатору автомобиля по возрастанию.

Идентификатор нужен, чтобы одинаковые баллы не давали случайный порядок.

### 11.14. Нет подходящих автомобилей

Если после обязательной фильтрации список пуст:

1. сохранить причины исключения всех кандидатов;
2. сгруппировать причины по ограничениям;
3. определить ограничение, которое исключило больше всего автомобилей;
4. показать его пользователю;
5. предложить изменить только это условие;
6. не выдавать нарушивший условие автомобиль как подходящий.

Можно показать блок «Ближайшие варианты для проверки», но каждая машина должна иметь явное описание нарушенного условия.

### 11.15. Псевдокод алгоритма

```ts
function recommend(profile: UserProfile, catalog: CatalogCar[]) {
  const normalized = normalizeProfile(profile)
  const evaluations = catalog.map((car) => evaluateConstraints(car, normalized))

  const eligible = evaluations.filter((item) =>
    item.constraints.every((constraint) =>
      constraint.state !== 'violated' &&
      constraint.state !== 'unknown'
    )
  )

  const scored = eligible.map((item) => {
    const rational = scoreRational(item.car, normalized)
    const emotional = scoreEmotional(item.car, normalized)
    const completeness = scoreCompleteness(item.car, normalized)
    const final = calculateFinalScore({ rational, emotional, completeness })

    return buildRecommendationCandidate({
      car: item.car,
      constraints: item.constraints,
      scores: { rational, emotional, completeness, final },
    })
  })

  const diversified = diversify(scored)
  const ranked = stableSort(diversified)

  return buildRecommendationRun({
    profile: normalized,
    candidates: ranked,
    excluded: evaluations.filter((item) => !eligible.includes(item)),
  })
}
```

Реальная реализация должна корректно обрабатывать неизвестные значения и не использовать сравнение объектов по ссылке для определения принадлежности к массиву.

## 12. Объяснения результатов

Объяснение строится из структурированных фактов, а не генерируется напрямую из общей анкеты.

Формат факта:

```ts
type ExplanationFact = {
  key: string
  type: 'match' | 'tradeoff' | 'unknown'
  label: string
  value?: string
  severity?: 'low' | 'medium' | 'high'
  sourceField: string
}
```

Примеры допустимых объяснений:

- подходит для городского сценария;
- рассчитан на нужное количество пассажиров;
- соответствует выбранной коробке передач;
- ближе к желаемому спокойному стилю;
- цена находится в верхней части бюджета;
- объём багажа меньше желаемого;
- данные о приводе отсутствуют.

ИИ может превратить факты в естественный текст только после получения `RecommendationCandidate`. AI-ответ должен проходить проверку, что в нём упоминаются только известные факты.

## 13. Адаптивный тест и дуэли

### 13.1. Библиотека вопросов

Создать `data/question-library.json`. Каждый вопрос должен иметь:

- стабильный идентификатор;
- тип ответа;
- поле профиля, которое изменяется;
- варианты ответа;
- условия показа;
- приоритет;
- возможность пропуска;
- текст для карточки;
- альтернативный текст без AI.

ИИ не создаёт обязательные поля с нуля. Он выбирает подходящие вопросы из библиотеки и может менять порядок.

### 13.2. Выбор следующего вопроса

Приоритет вопроса рассчитывать так:

```text
priority = businessImportance * uncertainty * estimatedImpact
```

Сначала задавать вопросы, которые:

- влияют на обязательные ограничения;
- исключают большую часть каталога;
- сильнее всего меняют итоговый рейтинг;
- часто остаются непонятыми пользователями.

### 13.3. Выбор пары для дуэли

Пары выбирать только среди автомобилей, прошедших обязательные условия. До формирования карточки дуэли отдельно выбирать её фокус. Пара без понятного различия для текущего профиля не должна показываться.

Для каждой пары сформировать список допустимых фокусов. Фокус должен:

- иметь подтверждённые значения у обоих автомобилей;
- показывать различие, которое можно описать короткой фразой;
- быть связанным с ещё неопределённой характеристикой пользователя;
- влиять на текущий порядок кандидатов или эмоциональный профиль;
- не повторять предыдущий фокус в этой сессии.

Оценка полезности фокуса:

```text
focusUtility =
  normalizedDifference * profileUncertainty * rankingImpact * readability
```

Если подходящего фокуса нет, пару не показывать. Если различие техническое, преобразовать его в понятную формулировку. Например, `clearanceMm` отображать как «выше клиренс для плохих дорог», а не как два числа без контекста.

Оценка полезности пары:

```text
pairUtility =
  styleDifference * uncertaintyOfDimension * candidateRelevance
```

В начале выбирать пары с заметным стилевым различием. В конце выбирать близкие варианты с высокой вероятностью изменения итогового порядка.

Не показывать повторную пару. Ограничить MVP пятью дуэлями с возможностью завершить раньше.

### 13.4. Обновление стиля после дуэли

Для выбранного автомобиля:

```text
userDimension += learningRate * (carDimension - userDimension)
```

Рекомендуемый `learningRate` — `0.15` для первой дуэли и постепенно уменьшать его до `0.08`.

Для ответа «оба нравятся» обновлять профиль в сторону среднего значения двух автомобилей с коэффициентом `0.05`.

Для ответа «ни один» обновление не выполнять, но сохранить отрицательный сигнал для этой пары.

После каждой дуэли пересчитывать временный рейтинг, но не показывать пользователю технические коэффициенты.

## 14. AI-слой

### 14.1. Интерфейс провайдера

```ts
interface AIProvider {
  parseUserDescription(input: string): Promise<ParsedProfile>
  selectQuestions(input: QuestionSelectionInput): Promise<QuestionSelection>
  explainRecommendations(input: ExplanationInput): Promise<string>
}
```

Создать два адаптера:

- `DeterministicAIProvider` для локального запуска без ключа;
- `OpenAICompatibleProvider` или другой подключаемый провайдер через переменные окружения.

### 14.2. Разбор свободного текста

AI должен возвращать строго типизированный JSON:

```ts
type ParsedProfile = {
  profilePatch: Partial<UserProfile>
  uncertainties: string[]
  clarificationQuestions: string[]
  confidence: number
}
```

После ответа провести Zod-валидацию. При ошибке использовать безопасный профиль и показать уточняющий вопрос.

### 14.3. Ограничения промпта

В системной инструкции AI закрепить:

- не придумывать технические характеристики;
- не называть автомобиль подходящим без результата движка;
- не менять обязательные условия;
- не раскрывать скрытый бюджет;
- возвращать JSON по схеме;
- помечать неоднозначность;
- использовать только переданные факты каталога.

### 14.4. Объяснение через AI

Передавать модели:

- профиль без лишних персональных данных;
- список рекомендованных автомобилей;
- структурированные совпадения;
- компромиссы;
- неизвестные значения;
- версию каталога.

Не передавать в prompt весь каталог, если достаточно отобранных кандидатов.

## 15. API и серверные функции

### `POST /api/recommendation`

Принимает профиль и возвращает `RecommendationRun`.

Проверки:

- схема профиля через Zod;
- размер запроса;
- допустимые значения enum;
- версия каталога;
- отсутствие неизвестных полей в обязательных условиях.

### `POST /api/ai/parse-profile`

Принимает свободный текст. Возвращает проверенный `ParsedProfile`. При отсутствии AI-ключа использует детерминированный разбор ключевых слов и возвращает низкую уверенность.

### `POST /api/ai/questions`

Возвращает список идентификаторов вопросов из библиотеки. Сервер должен отфильтровать ответ AI и удалить неизвестные идентификаторы.

### `POST /api/auth/demo`

Принимает только разрешённый `demoKey` из списка конфигурации и создаёт серверную сессию демо-пользователя. Клиент не передаёт идентификатор произвольного пользователя.

Ответ содержит:

- текущего демо-пользователя;
- его профиль;
- ссылку на гараж;
- признак `isDemo: true`.

Сервер должен отклонять неизвестный `demoKey`, не раскрывать список существующих ключей и ограничивать частоту запросов.

### `POST /api/auth/demo/reset`

В режиме разработки и демонстрации сбрасывает данные выбранного демо-пользователя к seed-состоянию. В production доступ к endpoint разрешён только через административный флаг или полностью отключён.

### `GET /api/catalog`

Возвращает каталог или его публичную часть. Скрывать внутренние заметки, если они существуют.

### `POST /api/garage`

Создаёт запись в гараже. Проверяет, что `carId` существует в текущей версии каталога.

### `PATCH /api/garage/:itemId`

Изменяет статус, заметку и видимость записи только владельцем.

### `DELETE /api/garage/:itemId`

Удаляет или архивирует запись владельца.

### `POST /api/share`

Создаёт ссылку с областью доступа и сроком действия по желанию.

### `DELETE /api/share/:token`

Отзывает ссылку владельца.

### `POST /api/friends/request`

Создаёт запрос дружбы по коду или ссылке.

### `PATCH /api/friends/request/:id`

Принимает или отклоняет запрос.

## 17. Модель PostgreSQL и SQLAlchemy

Использовать PostgreSQL как основную базу данных и SQLAlchemy 2.0 как ORM. Все изменения схемы выполнять через Alembic migrations.

Минимальные таблицы:

- `users` — аккаунты, email, парольный хеш, флаг `is_demo`, `demo_key`;
- `profiles` — отображаемое имя, аватар, видимость, стиль;
- `garages` — один гараж владельца;
- `garage_items` — сохранённые автомобили, статус, заметка, видимость и версии;
- `share_links` — токен, область доступа, срок действия и отзыв;
- `friend_requests` — отправитель, получатель, статус;
- `friendships` — подтверждённые связи;
- `recommendation_runs` — профиль, версии, статус и JSON результата;
- `duel_sessions` — сессия дуэлей и временный профиль;
- `duel_choices` — выбор пользователя, фокус и пара автомобилей.

Требования к схеме:

- идентификаторы использовать UUID или безопасные случайные строки;
- `users.email` сделать уникальным при наличии email;
- `garage_items` защитить уникальным индексом `(garage_id, car_id)`;
- `friend_requests` защитить от дублирующего запроса;
- `share_links.token` сделать уникальным;
- добавить индексы для `user_id`, `garage_id`, `car_id`, `visibility`, `created_at`;
- JSON-поля использовать для версионируемого профиля и результата, но связи пользователей и права доступа хранить в отдельных колонках;
- демо-аккаунты хранить с `is_demo = true`;
- seed-скрипт должен быть идемпотентным и повторный запуск не должен создавать дубли.

Пример SQLAlchemy-модели пользователя:

```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[UUID] = mapped_column(primary_key=True, default=uuid4)
    email: Mapped[str | None] = mapped_column(unique=True)
    password_hash: Mapped[str | None]
    display_name: Mapped[str]
    is_demo: Mapped[bool] = mapped_column(default=False)
    demo_key: Mapped[str | None] = mapped_column(unique=True)
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
```

Схемы Pydantic для API должны быть отдельными от SQLAlchemy-моделей. Нельзя возвращать ORM-объекты напрямую в HTTP-ответ.

## 20. Тестирование

### 20.1. Тесты алгоритма

Создать минимум следующие профили:

1. городской пользователь с автоматом и небольшим багажом;
2. семья из пяти человек с большим багажом;
3. путешествия и плохие дороги;
4. неизвестный бюджет;
5. пропущенные эмоциональные вопросы;
6. строгий бюджет;
7. обязательный электромобиль;
8. противоречивые ответы;
9. отсутствие подходящих моделей;
10. неизвестная характеристика у кандидата.

Проверить:

- обязательное ограничение никогда не нарушается;
- неизвестное значение не считается выполненным;
- одинаковый профиль даёт одинаковый порядок;
- изменение ответа меняет результат, если поле влияет на рейтинг;
- нет дублей одной модели;
- нет искусственного заполнения списка;
- причины соответствуют фактам.

### 20.2. Тесты AI-слоя

- корректный JSON;
- некорректный JSON;
- неизвестный идентификатор вопроса;
- выдуманная характеристика;
- пустой ответ;
- отключённый AI-провайдер;
- неоднозначное описание;
- слишком длинный текст.

### 20.3. End-to-end тесты

Минимальные сценарии Playwright:

1. открыть главную и начать тест;
2. пройти тест с пропуском вопроса;
3. пройти дуэль;
4. получить результат;
5. изменить ответ и увидеть пересчёт;
6. сохранить автомобиль в гараж;
7. открыть гараж;
8. создать ссылку;
9. открыть ссылку в новом контексте;
10. проверить, что приватная заметка не видна.

## 24. Критерии приёмки

### Подбор

1. Пользователь может начать подбор без регистрации.
2. Можно описать желание свободным текстом или выбрать готовые варианты.
3. Можно пропустить необязательный вопрос.
4. Обязательные условия применяются до ранжирования.
5. Автомобиль с нарушенным обязательным условием не попадает в подтверждённые рекомендации.
6. Одинаковые входные данные дают одинаковый порядок.
7. В результате есть реальные автомобили из каталога.
8. Для каждой рекомендации есть совпадения, компромиссы и неизвестные данные.
9. При изменении ответа происходит новый расчёт.
10. При нулевом результате показывается причина.

### Дуэли

1. Пара выбирается только из допустимых автомобилей.
2. Повторные пары не показываются.
3. В карточке видны только 1–3 различающих признака, выбранных алгоритмом для этой пары.
4. Полная таблица технических характеристик не показывается в дуэли.
5. Ответы «оба» и «ни один» обрабатываются отдельно.
6. После дуэли меняется временный профиль вкуса.
7. После завершения дуэлей пересчитываются результаты.

### Гараж и друзья

1. Машина сохраняется из результата.
2. Можно изменить статус и заметку.
3. Приватная заметка не отображается по публичной ссылке.
4. Ссылку можно отозвать.
5. Гараж не показывает бюджет без разрешения.
6. Дубли одной машины не создаются.
7. Друг видит только разрешённые записи.

### AI

1. Сайт работает без AI-ключа.
2. AI-ответ проходит схему валидации.
3. Неизвестные поля помечаются как неопределённые.
4. AI не меняет обязательные ограничения.
5. AI не добавляет технические факты, которых нет в каталоге.

### Демо-аккаунты

1. На странице регистрации есть отдельный блок «Посмотреть демо».
2. Жюри может открыть каждый демо-профиль одним нажатием.
3. В каждом демо-профиле есть заполненный гараж и готовый результат подбора.
4. Демо-аккаунт помечен флагом `isDemo`.
5. Демо-данные можно сбросить к исходному состоянию.
6. Демо-профили не содержат персональных данных.
7. Обычная регистрация и демо-вход визуально и логически разделены.
